Thin harness (ADR-0083)
¶
Frontier alignment refactor. Explicit planning DAG не строится поверх reasoning-моделей. Применяются
reasoning_effort
+ prompt caching + principle-based prompts. Эмпирическая валидация: 85.7% Pass¹ на τ²-retail benchmark'е с mid-tier моделью Gemini 3.5 Flash — паритет с Sonnet 4.5 reference (86.2%).
Контекст
¶
Phase A → B → B+ harness optimizations (ADR-0079 PEV middleware, ADR-0080 typed plan, ADR-0081 PredicateWriteVerifier) обеспечили стабильный потолок 55% Pass¹ на τ²-retail. Гипотеза: «потолок gpt-5.4-mini в данной harness».

Толстый и тонкий harness
¶
Толстая архитектура
¶
graph TB
    U[User msg] --> P[Planner subagent<br/>LLM call #1]
    P --> S[Structured plan<br/>steps + verifies]
    S --> E[Executor agent<br/>LLM call #2 ... #N]
    E --> V[PostWriteVerifier<br/>predicate eval]
    V -->|fail| E
    V -->|pass| C[Critique LLM call<br/>outcomes grader]
    C --> Final[Final answer]
Конструкция: explicit planning DAG, отдельный planner subagent создаёт typed plan, executor выполняет шаги, verifier проверяет predicates. Паттерн стал популярен в 2024 в LangGraph, CrewAI, AutoGen.
Проблема: для reasoning-моделей (gpt-5.x, o-series, Sonnet 4.5+) конструкция избыточна. Модель выполняет «think step-by-step» внутренне эффективнее, чем внешний scaffolding.
Тонкая архитектура
¶
graph TB
    U[User msg] --> H[Harness loop]
    H -->|reasoning_effort=high| L[LLM call<br/>inline план + tool use]
    L -->|tool calls| T[Tools]
    T --> L
    L -->|final| Final[Final answer]
Исключено:
Explicit planner subagent (ADR-0079 Phase 3).
Wave-based state graph.
External plan validation на каждом шаге.
Добавлено:
reasoning_effort="high"
(B.1 + B.3).

headroom (B.3).
Prompt caching (B.6 — автоматически для OpenAI/Anthropic compatible providers).

Principle-based prompts вместо ALWAYS/NEVER imperatives.

B.5. Tool Use Examples
¶
inspect_user
,
inspect_order
,

— failure case, документированный в Doc («wrong tool selection when tools have similar names»). Каждый получает в description блок:
Example: inspect_order(order_id='#W2378156')
Returns: {order: {...}, products: [...], user: {...}}
Use when: user mentions a specific order id and you need its items / status / owner.
Don't use when: you only have a user_id — call inspect_user(user_id) instead.
B.6. Prompt caching
¶
gpt-5.4-mini через OpenRouter (OpenAI provider) поддерживает automatic prompt caching для prefix ≥1024 tokens на repeated requests. Required ordering:
tools → system → user messages
. В AgenticOS этот порядок реализован.
Explicit
cache_control
блоки не требуются для OpenAI моделей. Для Anthropic — добавляются явные блоки.
Исключения refactor'а
¶
Из §«Что НЕ меняем» ADR-0083:
MCP migration.
Tool count — 31. JSON function calling работает. Документированный threshold для MCP: >10 tools или >3 chained calls с heavy chain. Marginal benefit, major migration cost.
Code Execution / CodeAct.
Тот же threshold.
Multi-agent orchestrator-worker.
Для shared-state задач (coding, tau2-retail) hurts. В AgenticOS присутствует
delegate
(ADR-0050–0053) для специфических задач, но не как default.
Context compaction at >70% window.
Retail-сессии содержат 30–40 messages, что не приближается к 70% context window gpt-5.4-mini (256k).
Lazy MCP loading / Tool Search Tool.
Не применимо при отсутствии MCP migration.
Firecracker / E2B sandbox.
InProcessBackend
для evals (trusted Python);
GVisorBackend
для production tools.
Empirical revert: возврат planner subagent
¶
20-task batch result после Variant B (planner removal): 9/20 = 45% Pass¹, регрессия -10 ppt относительно baseline 11/20 = 55%.
Forensic re-run 11 fails:
5/11 stochastic flips FAIL → PASS (45% variance). Single-trial noise dominates.
6/11 persistent fails на одинаковом паттерне wrong_write / scope_incomplete / wrong_variant.
Diagnostic на trace dumps (10 inspected): 0/10 traces вызвали
plan_track
(any op), 0/10 вызвали
memory_block
.
Следствие:
plan_structured
block не создавался.
PredicateWriteVerifier
(ADR-0081 B.3) silently no-ops на каждом dispatched write. Wrong-arg writes проходили без проверки.
Root cause.
Planner subagent был data dependency, feeding
plan_structured
через прямой
_persist_plan_structured
write — независимо от agent behavior. Агент с
reasoning_effort=high
следует system prompt'у буквально и пропускает meta-инструкцию
plan_track(op='set')
в §5 «Required first-turn protocol».
Lesson.
Документированное «don't build planning DAG with reasoning models» — true для general agentic loops, но в специфической конфигурации gpt-5.4-mini в данной harness планер выполняет роль block-writer'а независимо от reasoning capability модели. Модель планирует внутренне, но не externalises; результат — downstream deterministic verification теряет данные.
Применённое revert.
use_planner_subagent=True
default в
HarnessAgentDriver
. B.1–B.3, B.5–B.6 retained. Planner subagent runs once на первом user turn, пишет блоки
plan
(markdown) и
plan_structured
(JSON) до первого turn'а executing agent.
PredicateWriteVerifier
получает данные для evaluation.
«Thin harness» не является absolute principle, а context-dependent наблюдением. Reasoning models сокращают некоторые потребности в scaffolding, но не все. Empirical measurement приоритетнее документной генерализации.
Гарантии refactor'а
¶
Token cost:
reasoning_effort=high
добавляет thinking tokens (5–30k на call).
max_tokens=300k
обеспечивает headroom. Net cost per task: от $0 (gpt-5.4-mini base) до $0.005–0.01 с reasoning.
Wall time: thinking добавляет латентность 20–60 секунд на task. Trade-off приемлем для customer-service Pass¹.
Backward compatibility: existing Harness consumers не требуют изменений.
reasoning_effort
и
max_tokens
optional с safe defaults.
Запрещено:
reasoning_effort
для не-reasoning моделей (claude-haiku-3.5). API rejects. Соответствие effort и model class — ответственность driver'а.

Анти-паттерны
¶
Конструирование explicit planning DAG до получения эмпирического доказательства, что он повышает Pass¹ на используемом model class.
ALWAYS / NEVER правила в system prompt'е. Указывают на underlying bug (см. ADR-0076 anti-pattern detection).
Wave-based state machine при Pass¹ <30%. Фундаментальная проблема — не в harness layout.
