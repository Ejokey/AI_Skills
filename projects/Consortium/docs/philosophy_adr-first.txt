ADR-first дисциплина
¶
Каждое архитектурное решение фиксируется как Architecture Decision Record до кода. Это не «best practice», а конструктивный минимум, без которого многосессионный проект через 10 итераций теряет согласованность.
Мотивация
¶
Разработка AgenticOS — многомесячный многосессионный проект. Условия эксплуатации Claude Code как ассистента:
Контекст уплотняется при компрессии. Часть истории заменяется на summary, детали утрачиваются.
Сессии конечны. Новая сессия начинается с пустого контекста.
Между сессиями могут проходить дни и недели.
Через 10–20 сессий теряется и человеческая память. Вопрос «почему был выбран Firecracker?» через год не имеет владельца ответа.
Без явной инфраструктуры персистентности проект через десяток сессий теряет согласованность:
Разные модули написаны в разных конвенциях.
Уже принятые архитектурные решения переоткрываются и «уточняются» в противоречивых направлениях.
Появляются дубли исследований, поскольку результаты прошлых не сохранены.
Тесты постепенно перестают отражать реальный контракт: код мутирует, инварианты не зафиксированы.
Архитектурная задача: построить разработку так, чтобы любая будущая сессия восстанавливала полное понимание проекта за 10 минут и продолжала с точки остановки предыдущей.

Слой 3. Mechanical invariants
¶
Самый надёжный слой персистентности: не зависит от памяти Claude или дисциплины записи. Нарушение инварианта приводит к красному CI.
Типы
(
pyright --strict
). Сигнатуры функций фиксируют контракт точнее любой документации.
Линтер
(
ruff
).
Тесты на контракты подсистем
, не только на код. Если ADR утверждает «brain не имеет прямого доступа к credentials» — должен существовать тест, проверяющий это runtime.
import-linter
— структурные инварианты (10 контрактов): запрет импортов из
hands/
в

и аналогичные.

Принцип: что проверяется машинно — проверяется машинно. ADR — для людей, тесты — для машин.

Формат ADR
¶
Имя файла:
docs/adr/NNNN-kebab-case.md
, где
NNNN
— монотонно растущий номер. Номера не переиспользуются.
# ADR-NNNN: Заголовок одной фразой
-
**Статус:**
Proposed | Accepted | Deprecated | Superseded by NNNN
-
**Дата:**
YYYY-MM-DD
-
**Связано:**
ADR-XXXX, файл docs/architecture/...
## Контекст
Проблема, мотивация, ограничения.
## Варианты
-
**A — Вариант 1.**
Плюсы и минусы.
-
**B — Вариант 2.**
Плюсы и минусы.
-
**C — Вариант 3.**
Плюсы и минусы.
## Решение
Выбран вариант X. Обоснование.
## Последствия
-
Что становится обязательным после принятия.
-
Что становится запрещённым.
-
Что потребуется пересмотреть.
## Когда пересматривать
Триггеры, при которых ADR теряет актуальность.
Правила
¶
ADR пишется до кода, который его реализует. При обратном порядке кодовая база становится единственным источником истины, обоснование решения теряется через сессию.
Желание сделать иначе через несколько сессий оформляется новым ADR со статусом
Supersedes NNNN
. Старый ADR не редактируется.
Принятые (Accepted) ADR иммутабельны по смыслу. Исправление опечаток и формулировок допустимо.
Tech-debt triage (ADR-0086)
¶
Архитектурное решение часто имеет deferred scope — задачи, которые сейчас не закрываются, но должны быть учтены. До ADR-0086 эти пункты жили в секциях «Когда пересматривать» отдельных ADR и в записях
Не сделано в этой Фазе
журнала
STATUS.md
. После 90 сессий формат стал unreadable.
ADR-0086 ввёл централизованный реестр
docs/tech-debt.md
с таксономией приоритетов:
Приоритет
Семантика
P0 — critical
Блокирует production claim, нарушает security invariant (
CLAUDE.md §1-9
), представляет реальный production risk
P1 — significant
Accepted limitation. Не блокирует текущие use cases, пересматривается при появлении нового scenario
P2 — wishlist
Speculation, feature creep, premature feature. Реализуется при clear demand signal
Каждый item содержит:
ID
(TD-NNN).
Title
.
Source
— ADR происхождения.
Pri
.
Status
:
Open
,
Resolved (YYYY-MM-DD, optionally superseded by ADR-NNNN)
,
Reclassified
.
Текущее состояние v2.1: 0 P0 + 0 P1 + примерно 10 open P2 (trigger-driven).
Протокол сессии
¶
Из
CLAUDE.md
.
В начале каждой сессии — порядок чтения:
CLAUDE.md
— принципы.
docs/ROADMAP.md
— фаза.
docs/STATUS.md
— последние 1–2 записи журнала.
По мере необходимости —
docs/adr/
,
docs/architecture/
,
docs/research/
.
Во время работы:
Любое архитектурное решение → новый ADR в
docs/adr/NNNN-kebab-case.md
. Номера монотонно растут.
Любое изменение контракта подсистемы → обновление соответствующего
docs/architecture/*.md
.
При расхождении с уже зафиксированным ADR — открыть новый ADR со статусом
Supersedes NNNN
. Прямое редактирование старого ADR запрещено.
В конце сессии:
Запись в
docs/STATUS.md
в самый верх (обратный хронологический порядок).
Если есть незакоммиченные изменения — коммит с осмысленным сообщением. Push без явного запроса не выполняется.
Анти-паттерны
¶
«Я помню» как стратегия.
Незаписанное решение через сессию переоткрывается или теряется.
Хранение project state в memory Claude.
Memory предназначена для рабочих привычек, не project state.
CLAUDE.md
как мусорка.
Превышение 200 строк требует рефактора с выносом деталей в
docs/
.
Редактирование принятых ADR.
Только новые ADR со ссылкой
Supersedes
.
Документация после кода.
Документация ADR пишется перед кодом. Иначе код становится единственным источником, обоснование забывается через сессию.
Один большой документ на всё.
Длинные документы вытесняются при компрессии и не находятся при поиске.
Слияние brain + hands + session «временно».
Архитектурные инварианты нарушаются один раз и навсегда.
Эффект на длинном горизонте
¶
После 101 ADR и 98 сессий за полгода:
0 архитектурного дрейфа — каждое решение прослеживается через
git log
+ ADR + STATUS.
0 неустановленного происхождения. Для любого участка кода существует ADR.
Tech-debt registry: 0 P0 + 0 P1. Все «не сделано в этой фазе» зафиксированы и проходят через triage.
Replay-готовность процесса. Новая сессия Claude восстанавливает полное понимание за 10 минут чтения
CLAUDE.md
→
ROADMAP.md
→ 1–2 STATUS записей.
Это не педантичность. Это operating system for development process.
