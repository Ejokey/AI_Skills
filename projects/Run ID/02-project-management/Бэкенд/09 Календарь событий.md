# RUN.ID — бэкенд: календарь событий. Что сделать

Документ для бэкенд-разработчика. Раздел заявлен в UX-брифе как P1.

---

## Текущее состояние

**На фронте:** страницы календаря событий нет. В навигации четыре пункта — Лента активностей, Тренировки, Карта, Привилегии. Событий нет нигде.

**В админке:** ресурс `Events` присутствует в меню, список пуст («No events»), форма создания **не содержит ни одного поля** — только кнопки Create / Cancel. Каркас отскаффолжен, модель не заполнена.

Итого: сущность заведена номинально, реализации нет ни на одной стороне.

---

## 1. Модель события

По UX-брифу карточка события содержит: **название, дату, организатора**. Список сортируется по дате, **прошедшие события не показываются**.

**Сделать:** заполнить модель и Filament-ресурс. Минимальный набор:
- название;
- дата и время проведения;
- организатор;
- описание;
- место проведения;
- ссылка на регистрацию или сайт события;
- изображение/афиша;
- признак публикации, чтобы готовить событие заранее и публиковать по готовности.

**Продумать:**
- Нужны ли события длительностью в несколько дней (дата начала и окончания) или достаточно одной даты. Марафонские выходные и фестивали обычно многодневные.
- Место проведения — просто текст или координаты с показом на карте. Если координаты, встаёт вопрос, не должны ли события отображаться на общей карте наравне с Run-Friendly местами. Для MVP скорее текст; решение зафиксировать явно.
- Нужна ли привязка события к городу для фильтрации. При десятке событий не нужна, при федеральном охвате — обязательна.

---

## 2. Выдача списка

**Сделать:**
- Список предстоящих событий, отсортированный по дате возрастания.
- **Прошедшие не показывать** — фильтрация по дате на сервере, а не скрытие на фронте.
- Лимит на количество возвращаемых записей.

**Продумать:** что считать «прошедшим» для многодневного события — оно должно уходить из списка по дате окончания, а не начала. Связано с вопросом о многодневности выше.

---

## 3. Кто заводит события

По аналогии с Run-Friendly местами — только администратор. Пользовательского создания событий в MVP нет.

**Сделать:** ограничить создание и редактирование администратором. Публичный API — только на чтение.

**Продумать:** нужна ли запись/регистрация пользователя на событие. В UX-брифе этого нет — только просмотр списка. Если регистрация появится, это отдельная сущность участия и заметно больший объём. Не закладывать сейчас, но и не делать модель так, чтобы её нельзя было потом добавить.

---

## 4. Открытые вопросы к продакту

1. **Нужен ли календарь в MVP вообще.** Он числится P1 (не блокирует старт), сущность пуста с обеих сторон, страницы на фронте нет. Если релиз близко — разумнее осознанно перенести за MVP, чем делать наспех. Решение продакта.
2. **Откуда берётся контент.** События — быстро устаревающий контент, требующий регулярного ведения. Нужен ответ, кто и с какой периодичностью их заводит. Пустой раздел «Календарь событий» на проде выглядит хуже, чем его отсутствие.
3. **Есть ли макеты.** В переданных финальных макетах экрана календаря не было. До вёрстки нужен дизайн — иначе бэкенд будет угадывать состав полей.
