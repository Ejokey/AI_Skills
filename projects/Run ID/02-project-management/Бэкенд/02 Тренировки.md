# RUN.ID — бэкенд: загрузка и просмотр тренировки. Что осталось сделать

Документ для бэкенд-разработчика. Основан на прогоне реального сценария на дев-стенде `runid.devvm7.mobipark.ru` (загружен `.gpx` с часов Zepp, пройден путь загрузка → редактирование → сохранение → детальная страница → список), сверке с финальными макетами экранов и с BRD.

**Приоритет — бег.** Метрики, формулы и логика затачиваются под беговой сценарий; см. раздел 8 про мультиспорт.

**Happy path уже работает** и переделывать его не нужно: парсинг `.fit/.gpx/.tcx`, извлечение метрик (дистанция, время в движении, набор высоты, средний темп, пульс ср./макс., каденс), автогенерация названия, экран редактирования, детальная страница со сплитами по км и картой, список тренировок с поиском и фильтром по типу.

Ниже — только то, чего не хватает. Каждый пункт: что сделать + почему (если проверено вживую — указано, как воспроизвести).

## 1. Обработка краевых случаев при загрузке — главный пробел

Сейчас реализован только успешный сценарий. BRD (раздел 4.3) требует четыре состояния обработки: `processing` → `processed` / `failed` / `duplicate`. Из них есть одно.

### 1.1 Дубликаты не отлавливаются — ПОДТВЕРЖДЕНО

**Как воспроизвести:** загрузить один и тот же файл дважды. Результат: создаются две независимые тренировки (на стенде это id `31` и `32` — одинаковые название, дата, дистанция, время, пульс). Никакого предупреждения.

**Сделать:**
- Определять дубликат до создания записи. Критерий определить самостоятельно, но не по имени файла — оно ненадёжно. Рабочий вариант: хэш содержимого файла + связка `user_id`; более устойчивый — совпадение по `user_id` + время старта активности + длительность (с допуском в несколько секунд), это ловит одну и ту же тренировку, выгруженную из двух источников в разных форматах.
- Вернуть фронту статус `duplicate` со ссылкой на существующую тренировку, чтобы он показал «эта тренировка уже загружена» вместо создания копии.
- Решить, разрешать ли принудительную загрузку поверх («всё равно загрузить») — предложить продакту, самостоятельно не вводить.

### 1.2 Файл без GPS-данных принимается как успешный — ПОДТВЕРЖДЕНО

**Как воспроизвести:** загрузить валидный по XML `.gpx`, в котором `<trkseg>` пустой (без точек). Результат: создаётся тренировка (на стенде id `33`), показывается баннер «Файл загружен и разобран — проверьте и сохраните детали», при этом все метрики пустые («—»), карта — «Трек недоступен».

**Сделать:**
- Валидировать после парсинга: если в треке нет ни одной точки с координатами (или нет ни одной метрики) — это `failed`, а не `processed`. Запись тренировки не создавать, вернуть внятную ошибку («в файле нет GPS-данных»).
- Отделить «файл разобран, но часть метрик отсутствует» (это нормально — см. п.4) от «разбирать нечего» (это ошибка).

### 1.3 Не проверены, но нужны — проверить и закрыть

- **Неподдерживаемый формат.** Серверная проверка обязательна независимо от фронтовой: определять тип по содержимому, а не по расширению.
- **Битый/невалидный файл** (обрезанный `.fit`, невалидный XML) — не должен ронять обработчик, должен отдавать `failed` с причиной.
- **Ограничение размера.** BRD называет 20 МБ. Проверить, что лимит есть на сервере и что превышение отдаёт понятную ошибку, а не 500 или таймаут.

### 1.4 Обработка синхронная — при больших файлах сломается

Сейчас после выбора файла происходит короткая «загрузка» и сразу редирект на `/activities/{id}/edit`, то есть парсинг идёт в рамках запроса. Тестовый `.gpx` весил 700 КБ. `.fit` с многочасовой тренировки и посекундной записью будет ощутимо тяжелее.

**Сделать:**
- Вынести парсинг в фоновую обработку, отдавать `processing` сразу и не держать HTTP-запрос.
- BRD прямо требует, чтобы статус был **неблокирующим**: пользователь может уйти на другой экран, а тренировка дообработается. Нужен endpoint статуса обработки (или пуш через уведомления — они на стенде уже есть).

**Продумать:** насколько это критично для MVP при реальных объёмах. Если решение — оставить синхронно, зафиксировать осознанно и померить время обработки на самом тяжёлом реальном `.fit`, а не на тестовом gpx.

## 2. Чего нет на стенде из того, что есть в макетах

Всё перечисленное отрисовано в финальных макетах, но на дев-стенде отсутствует. Это новые бэкенд-задачи, а не дефекты.

### 2.1 Фотографии тренировки — отдельный блок

В макете детальной страницы есть блок «Фотографии тренировки» — галерея из нескольких снимков.

**Сделать:** загрузку, хранение и отдачу изображений, привязанных к тренировке. Понадобится: лимит количества и размера файла, допустимые форматы, порядок отображения, удаление отдельного фото, генерация превью (в галерее показываются уменьшенные, открывать полноразмерные при просмотре).

**Продумать:**
- Где загружаются фото — на экране редактирования тренировки (в макете редактирования блока загрузки нет) или отдельным действием на детальной странице. Вопрос к дизайнеру.
- Видимость фото должна подчиняться настройке приватности самой тренировки (см. раздел 3), а не быть публичной всегда.

### 2.2 Счётчик просмотров

В макете рядом с лайками показан счётчик просмотров (иконка глаза).

**Сделать:** учёт просмотров тренировки. Определить правило подсчёта, иначе цифра будет бессмысленной: не считать просмотры автора, не накручивать при каждом обновлении страницы одним и тем же пользователем (разумно — один просмотр на пользователя в сутки), считать только для тренировок, доступных зрителю по приватности.

### 2.3 Место проведения тренировки

В макете под названием указано место: «Эрмитаж, Санкт-Петербург, Россия». На стенде этого нет.

**Сделать:** обратное геокодирование стартовой точки трека при обработке файла, результат сохранять в тренировке. Геокодировать один раз при разборе, а не при каждом открытии страницы.

**Продумать:** если у пользователя настроена приватная зона (см. п. 5), название места может выдать домашний адрес. Показ места должен учитывать приватные зоны — либо не показывать вовсе, либо огрублять до города.

### 2.4 Личная заметка — второе текстовое поле

В макете редактирования два разных текстовых поля: «Описание (необязательно)» и отдельное поле с подсказкой «Личная заметка о покрытии на маршруте».

**Сделать:** отдельное поле в модели тренировки. Судя по названию, это **приватная заметка для себя**, а не публичное описание — значит должна отдаваться только автору и никогда не попадать в ответ для чужого зрителя, независимо от настройки приватности самой тренировки.

**Продумать:** подтвердить у дизайнера, что заметка действительно приватная. Если она публичная — задача сводится к добавлению второго текстового поля, но правило видимости всё равно нужно зафиксировать явно, а не оставлять на усмотрение фронта.

### 2.5 Тип тренировки должен меняться вручную

В макете редактирования тип — выпадающий список с возможностью выбора. На стенде это статичная подпись «Бег», изменить нельзя.

**Сделать:** принимать изменение типа активности при сохранении. Автоопределение типа из файла остаётся, но становится значением по умолчанию, которое пользователь может переопределить (часы часто пишут неверный тип).

## 3. Приватность тренировки — серверная проверка

На экране редактирования есть выбор «Кто может просматривать»: **Все пользователи / Подписчики / Только я** — приватность задаётся **у каждой тренировки**, а не только на уровне профиля.

**Сделать:**
- Проверку доступа на чтение тренировки выполнять на сервере по полю самой активности. Нельзя опираться на то, что фронт не покажет ссылку: прямой запрос `/activities/{id}` чужой приватной тренировки должен отклоняться.
- «Подписчики» = проверка наличия подписки запрашивающего на автора, на момент запроса.
- То же ограничение применить к ленте активностей и к списку тренировок в чужом профиле — приватная тренировка не должна попадать в выдачу.
- Распространить правило на всё содержимое тренировки: фотографии (п. 2.1), место проведения (п. 2.3), трек, сплиты.

**Продумать (вопрос к продакту, ответ нужен до реализации):**
- Как поле приватности тренировки соотносится с настройкой приватности профиля (там тоже три значения). Варианты: настройка профиля = дефолт, который подставляется в новую тренировку и переопределяется; или профиль = жёсткий потолок (приватный профиль скрывает всё, независимо от настройки тренировки). Это разные реализации, выбрать одну и зафиксировать.

## 4. Права на чужие тренировки

В списке своих тренировок у каждой строки есть иконки «Редактировать» и «Удалить». В макете чужого профиля явно указано, что там их быть не должно.

**Сделать:** серверную проверку владения в endpoint'ах редактирования и удаления тренировки — отклонять, если `activity.user_id != current_user.id`, независимо от того, что рисует фронт. Это тот же класс проверки, что и в разделе 3, и он уже был в бэкенд-брифе по профилю и соцчасти — здесь повторён, потому что относится к этому же разделу.

## 5. Опциональные метрики — не считать обязательными

При загрузке реального файла с часов поле «Калории» осталось пустым. Это нормальное поведение: набор метрик зависит от того, что записал конкретный прибор.

**Сделать:** трактовать как опциональные (nullable) и корректно отдавать отсутствие значения: калории, пульс (ср./макс.), каденс, набор высоты. Отсутствие любой из них не должно приводить к ошибке обработки, к пустому экрану или к `failed` — файл всё равно валиден, если есть трек. Не подставлять нули вместо отсутствующих значений: «0 ккал» и «нет данных» — разные вещи, фронт показывает их по-разному («—»).

## 6. Чего нет ни на стенде, ни в макетах, но требует BRD

- **Графики темпа / пульса / высоты** по ходу тренировки (BRD 4.4). Сейчас есть только таблица сплитов; в финальных макетах графиков тоже нет. Похоже на сознательное упрощение — но это надо подтвердить, а не считать по умолчанию. Если делаем — нужен endpoint, отдающий ряды точек (время/дистанция → темп, пульс, высота), а не только агрегаты.
- **Окраска трека по темпу/пульсу** с переключателем (BRD 4.4) — трек одноцветный и в макетах тоже. Требует тех же поточечных данных, что и графики.
- **Privacy zones** (BRD 4.4, раздел 2 UX-брифа): обрезка публично видимого участка маршрута вокруг заданной пользователем точки. Не реализовано. Обрезка должна происходить **на сервере при отдаче чужому зрителю** — иначе полный трек всё равно уедет в API-ответ, и скрытие останется декоративным. Автор видит свой трек целиком. Связано с п. 2.3 (название места тоже может выдать адрес).

**Отложено сознательно (не брать сейчас):** блок «Сегменты» на детальной странице тренировки, обнаружение сегментов на треке и кнопка «Создать сегмент». В макете детальной страницы блок сегментов есть (с медалями за призовые места) — он войдёт в отдельный бриф по сегментам.

## 7. Регистрация: чего нет на бэке

Регистрации через мессенджер **MAX** и через **ВКонтакте** на бэке нет. Если эти способы входа появляются в макетах — они не в MVP-скоупе бэкенда, интеграцию с провайдерами сейчас не проектировать.

## 8. Мультиспорт: приоритет — бег

Продакт зафиксировал: **ориентир на бег**. Метрики, формулы (темп, каденс, калории) и вся логика обработки затачиваются под беговой сценарий.

При этом фактическое состояние такое:
- на стенде фильтр типов: Бег / Велозаезд / **Хайк** / Все;
- в макете списка тренировок: Бег / Велозаезд / Все — **Хайка нет**;
- BRD и UX-бриф фиксируют «только бег» как ограничение MVP, мультиспорт числится в Out-of-Scope.

**Сделать/уточнить:**
- Согласовать список типов с макетом — откуда взялся «Хайк», которого нет в дизайне. Либо убрать, либо добавить в макеты.
- Пока приоритет бег: не тратить время на корректные вело-формулы (скорость вместо темпа, мощность, другой расчёт калорий). Велозаезд может отображаться по беговым правилам, если продакт это принимает — но это надо принять явно, а не оставить как есть по умолчанию.

## 9. Мелкие расхождения макет ↔ стенд

- **Форматы файлов.** Модалка на стенде: «Доступные расширения .fit .gpx .tcx». В макете: «.fit .gpx» — без `.tcx`. Уточнить, поддерживаем ли `.tcx` (если да — макет надо поправить, если нет — убрать из приёма и с фронта, и с сервера).
- **Шаг подтверждения при загрузке.** В макете после выбора файла показывается состояние «Файл … успешно загружен» и пользователь **нажимает «Добавить»**. На стенде происходит автоматический редирект на экран редактирования, кнопку нажимать не требуется. Разное поведение; уточнить, какое считается правильным.
