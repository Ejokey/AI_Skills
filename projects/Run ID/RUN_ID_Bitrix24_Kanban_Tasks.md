## P0 — 10 карточек, заводить в Бэклог сразу

### 1. Регистрация / Вход

**Use Case (UC-01: Регистрация и создание профиля)**
Основной актор: Бегун. Новый пользователь регистрируется и создаёт базовый профиль бегуна.
Предусловия: пользователь имеет доступ к email или номеру телефона.
Триггер: открывает RUN.ID, нажимает «Зарегистрироваться».
Основной сценарий:
1. Пользователь вводит email/телефон и пароль.
2. Система проверяет уникальность email/телефона.
3. Система создаёт учётную запись и базовый профиль.
4. Система предлагает заполнить имя, аватар, единицы измерения.
5. Пользователь сохраняет профиль.
6. Система показывает главный экран (пустая лента/профиль).
Альтернативные сценарии:
- A1 (шаг 2): email/телефон уже зарегистрирован → предложить восстановить пароль или войти.
- A2 (шаг 1): некорректный формат email/телефона → ошибка валидации, продолжить нельзя.
Бизнес-правила: email/телефон уникальны в системе; пароль соответствует минимальным требованиям к длине и сложности.

**Элементы:** email/телефон + пароль, переключатель регистрация↔вход, ссылка на политику конфиденциальности.

**Состояния:**
- [ ] пустая форма
- [ ] ошибка формата
- [ ] email уже используется → войти/восстановить

**Ограничение:** 152-ФЗ — ссылка на политику конфиденциальности обязательна.

**Definition of Done:**
- [ ] UI/UX: макет всех 3 состояний утверждён
- [ ] Frontend: форма, клиентская валидация, переключение режимов
- [ ] Backend: регистрация/вход, проверка уникальности email

**Приоритет:** P0

### 2. Профиль (свой): статистика + настройки

**Use Case:** отдельного UC нет — это продолжение UC-01 (профиль создаётся при регистрации) плюс две user story:

US-02. Просмотр базовой статистики профиля
Как зарегистрированный бегун, я хочу видеть общий километраж, часы и число тренировок в своём профиле, чтобы ощущать прогресс.
Given у меня есть обработанные тренировки, When я открываю профиль, Then я вижу суммарные км, часы, количество тренировок.

US-03. Настройка профиля и видимости
Как зарегистрированный бегун, я хочу изменить аватар, единицы измерения и видимость профиля, чтобы персонализировать аккаунт и контролировать приватность.
Given я в настройках профиля, When меняю единицы измерения на мили и сохраняю, Then вся статистика в приложении отображается в милях.

**Элементы:** аватар, имя, суммарные км/часы/число тренировок, список последних тренировок, кнопка "Загрузить тренировку", ссылка на настройки, badge статуса членства. Настройки: аватар, единицы измерения, видимость профиля (публичный/только подписчики), удаление аккаунта.

**Состояния:**
- [ ] новый пользователь без тренировок → нули, не пустая заглушка

**Definition of Done:**
- [ ] UI/UX: макет профиля + подэкрана настроек
- [ ] Frontend: отображение статистики, форма настроек
- [ ] Backend: агрегация статистики, сохранение настроек

**Приоритет:** P0

### 3. Загрузка тренировки + статус обработки

**Use Case (UC-02: Загрузка и обработка тренировки)**
Основной актор: Бегун. Вторичный: Система (очередь/парсер). Бегун загружает файл тренировки (.fit/.gpx) с сайта производителя часов и получает обработанную тренировку с картой и статистикой.
Предусловия: пользователь авторизован, у него есть файл .fit/.gpx.
Триггер: нажимает «Загрузить тренировку», выбирает файл.
Основной сценарий:
1. Система принимает файл, создаёт запись со статусом «в обработке».
2. Ставит задачу на парсинг в очередь.
3. Парсер считает метрики (темп, пульс, высота, дистанция).
4. Система проверяет тренировку на дубликаты.
5. Система сопоставляет трек с существующими сегментами.
6. Система сохраняет тренировку, обновляет статистику профиля.
7. Пользователь видит обработанную тренировку: карту, графики, сводку, найденные сегменты.
Альтернативные сценарии:
- A1 (шаг 1): неподдерживаемый формат → ошибка загрузки, тренировка не создаётся.
- A2 (шаг 4): дубликат → помечается как дубликат, повторной записи в ленте нет.
- A3 (шаг 3): нет нужных данных (например, GPS-точек) → ошибка обработки.
Бизнес-правила: единственный способ получить тренировку в MVP — загрузка файла; дедупликация по времени, дистанции и хэшу файла.

**Элементы:** зона загрузки (.fit/.gpx, до 20 МБ), неблокирующий статус "в обработке" (можно уйти с экрана).

**Состояния:**
- [ ] processing → processed (редирект на детали)
- [ ] failed (нет GPS-данных)
- [ ] duplicate (уже загружена)
- [ ] неподдерживаемый формат при выборе файла

**Definition of Done:**
- [ ] UI/UX: макет зоны загрузки + всех 4 статусов
- [ ] Frontend: загрузка, поллинг статуса, неблокирующий UX
- [ ] Backend: парсинг .fit/.gpx, дедупликация, обработка ошибок формата

**Приоритет:** P0

### 4. Детали тренировки: карта + графики + сводка

**Элементы:** карта маршрута с окраской по темпу/пульсу (переключатель), графики темпа/пульса/высоты, таблица сплитов по км, сводка (ср./макс. темп и пульс, набор высоты, moving vs elapsed time, калории), список найденных сегментов, кнопка "Создать сегмент", лайк+счётчик.

**Состояния:**

**Ограничение:** обрезанный участок должен быть визуально обозначен, не "дырой" без объяснения.

**Definition of Done:**

### 5. Создание сегмента

**Use Case (UC-03: Создание сегмента)**
Основной актор: Бегун. Бегун выделяет участок своей тренировки и создаёт из него именованный сегмент для сравнения с другими.
Предусловия: авторизован, есть хотя бы одна обработанная тренировка.
Триггер: открывает тренировку, выбирает «Создать сегмент».
Основной сценарий:
1. Выделяет начальную и конечную точки участка на карте.
2. Задаёт название сегмента.
3. Система сохраняет сегмент (геометрию линии и дистанцию).
4. Система рассчитывает время прохождения как первую запись лидерборда.
5. Пользователь видит созданный сегмент и своё время.
Альтернативные сценарии:
- A1 (шаг 1): участок короче минимальной длины → предупреждение, просит выбрать длиннее.
- A2: сегмент с идентичной геометрией уже существует → предложить использовать существующий.
Бизнес-правило: сопоставление новых тренировок с сегментами — по упрощённому алгоритму (bounding box + пересечение линий).

**Элементы:** карта тренировки с выбором точек, поле "название сегмента".

**Состояния:**
- [ ] участок короче ~500 м → предупреждение
- [ ] сегмент с такой же геометрией уже есть → предложить существующий

**Definition of Done:**
- [ ] UI/UX: макет выбора точек + оба предупреждения
- [ ] Frontend: интерактивный выбор участка, форма названия
- [ ] Backend: валидация длины, поиск совпадений по геометрии

**Приоритет:** P0

### 6. Экран сегмента (лидерборд)

**Use Case (UC-04: Просмотр лидерборда сегмента)**
Основной актор: Бегун. Просматривает список лучших результатов на сегменте и своё место в нём.
Предусловия: сегмент существует, пользователь авторизован.
Триггер: открывает страницу сегмента.
Основной сценарий:
1. Система показывает список прохождений, отсортированный по времени.
2. Выделяет позицию текущего пользователя (если проходил).
3. Показывает личный рекорд пользователя.
Альтернативный сценарий:
- A1: пользователь ещё не проходил сегмент → общий лидерборд без выделения + призыв попробовать.

**Элементы:** название/карта сегмента, дистанция, список прохождений, выделенная позиция пользователя, личный рекорд.

**Состояния:**
- [ ] пользователь не проходил сегмент → лидерборд без выделения + CTA

**Definition of Done:**
- [ ] UI/UX: макет лидерборда + состояние "не проходил"
- [ ] Frontend: рендер списка, выделение своей позиции
- [ ] Backend: расчёт лидерборда и личного рекорда

**Приоритет:** P0

### 7. Лента активности подписок

**Use Case (UC-05: Подписка на бегуна и просмотр ленты)**
Основной актор: Бегун. Подписывается на другого пользователя, видит его тренировки в ленте, ставит лайк.
Предусловия: авторизован, целевой профиль существует.
Триггер: находит бегуна (поиск или ссылка на профиль), нажимает «Подписаться».
Основной сценарий:
1. Система создаёт асимметричную подписку (подписчик → автор).
2. Тренировки автора появляются в ленте подписчика в хронологическом порядке.
3. Пользователь просматривает ленту, ставит лайк.
4. Система сохраняет лайк, обновляет счётчик.
Альтернативный сценарий:
- A1: пользователь уже подписан → кнопка «Подписаться» становится «Отписаться».
Бизнес-правило: подписка асимметрична, не требует подтверждения второй стороной.

**Элементы:** хронологический список тренировок подписок (автор, дата, дистанция/время/темп, мини-карта, лайк+счётчик), переход в детали тренировки или профиль автора.

**Состояния:**
- [ ] пустая лента (нет подписок) → призыв найти и подписаться

**Definition of Done:**
- [ ] UI/UX: макет карточки ленты + пустое состояние
- [ ] Frontend: список карточек, переходы
- [ ] Backend: агрегация ленты по подпискам

**Приоритет:** P0

### 9. Моё членство + оплата

**Use Case (UC-06: Оформление цифрового членства с оплатой)**
Основной актор: Бегун. Вторичный: Платёжный шлюз (ЮKassa/Robokassa). Оплачивает разовый платёж и получает доступ к каталогу привилегий.
Предусловия: авторизован, нет активного членства.
Триггер: открывает «Членство», нажимает «Оформить членство».
Основной сценарий:
1. Система создаёт заказ со статусом «ожидает оплаты».
2. Инициирует платёж через шлюз, перенаправляет на страницу оплаты.
3. Пользователь вводит данные, подтверждает оплату.
4. Шлюз обрабатывает платёж, шлёт webhook об успехе.
5. Система активирует членство, открывает каталог привилегий.
6. Пользователь видит активное членство и каталог.
Альтернативные сценарии:
- A1 (шаг 4): платёж отклонён/отменён → заказ неуспешен, ошибка + повтор.
- A2: страница оплаты закрыта без завершения → статус «ожидает оплаты» до тайм-аута.
Бизнес-правило: в MVP только разовый платёж, без рекуррентных списаний.

**Элементы:** статус (нет членства / ожидает оплаты / активно / истекло), кнопка "Оформить членство" → оплата, автоактивация после оплаты.

**Состояния:**
- [ ] оплата отклонена/отменена → ошибка + повтор
- [ ] страница закрыта без оплаты → "ожидает оплаты" до тайм-аута

**Открытый вопрос → в "Требует обсуждения" до старта Frontend/Backend:** ЮKassa или Robokassa; устраивает ли разовый платёж без выбора тарифа на MVP.

**Definition of Done:**
- [ ] UI/UX: макет всех 4 статусов + перехода на оплату
- [ ] Frontend: экран статуса, интеграция виджета оплаты
- [ ] Backend: обработка webhook, активация членства, таймаут

**Приоритет:** P0

### 10. Каталог привилегий партнёров

**Use Case (UC-07: Просмотр каталога привилегий партнёров)**
Основной актор: Бегун с активным членством. Просматривает каталог привилегий и получает промокод/условия.
Предусловия: активное цифровое членство.
Триггер: открывает «Каталог привилегий».
Основной сценарий:
1. Система показывает список привилегий (2–3 партнёра на старте).
2. Пользователь выбирает привилегию.
3. Система показывает условия и промокод/инструкцию.
Альтернативный сценарий:
- A1: нет активного членства → каталог в ознакомительном режиме (без промокодов) + предложение оформить членство.
Бизнес-правило: каталог виден всем, промокоды — только с активным членством.

**Элементы:** список 2–3 партнёров (лого, описание привилегии), клик → условия + промокод.

**Состояния:**
- [ ] без членства → промокод скрыт, явный CTA "оформи членство"

**Открытый вопрос → в "Требует обсуждения":** какие именно 2–3 партнёра будут на старте — нужны лого/бренд-гайды.

**Definition of Done:**
- [ ] UI/UX: макет каталога + gated-состояние (паттерн переиспользуется в карточке 9)
- [ ] Frontend: список партнёров, скрытие промокода без членства
- [ ] Backend: отдача каталога, выдача промокода только с активным членством

**Приоритет:** P0

### 13. Настройки приватности (privacy zone)

**Use Case (UC-08: Настройка приватной зоны)**
Основной актор: Бегун. Задаёт приватную зону вокруг адреса, чтобы скрыть участок маршрута на публичной карте.

### 14. Удаление аккаунта

**User Story US-20 (право на забвение)**
Как бегун, я хочу удалить свой аккаунт и все связанные данные, чтобы реализовать своё право на забвение по 152-ФЗ.
Given я запросил удаление аккаунта, When запрос подтверждён, Then мой профиль и связанные персональные данные удаляются из системы в установленный срок.

**Элементы:** диалог подтверждения (повторный пароль/email-подтверждение) + предупреждение о необратимости.
