## Перед началом

1. `projects/<Клиент>/` — существующие материалы и ТЗ
2. `projects/<Клиент>/CONTEXT.md` — если есть
3. Нужный скилл из `skills/business-analysis/`:

| Задача | Скилл |
|---|---|
| Бизнес-требования | `brd-creation/` |
| Функциональные требования | `frs-creation/` |
| Use cases | `use-case-documentation/` |
| User stories | `user-story-writing/` |
| Критерии приёмки | `acceptance-criteria/` |
| Схемы процессов | `process-mapping/` |
| Потоки данных | `data-flow-diagrams/` |
| Модели требований (state, sequence, class) | `requirements-modeling/` |
| Сбор требований | `requirements-elicitation/` |

## Жёсткие правила

- **Требование, которого нет в источнике, — это твоё допущение.** Помечай такие явно
  отдельным разделом «Допущения», не смешивай с требованиями заказчика.
- **Не додумывай функциональность.** Пробел в ТЗ — это вопрос к человеку, а не место
  для твоей инициативы.
- **Вайрфреймы — только десктоп** (`memory/rules.md`). Мобильные версии не делай,
  пока не попросят явно.
- Не изобретай технологический стек, если он не задан — это решение команды.

## Что отдаёшь

Документ в `projects/<Клиент>/` + список открытых вопросов и допущений отдельно.
