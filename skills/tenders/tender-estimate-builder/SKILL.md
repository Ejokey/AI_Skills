# Tender Estimate Builder

Скилл для расчёта и обоснования стоимости. Работа делится на три разных задачи, которые
часто путают:

| Задача | Что на выходе | Точность |
|---|---|---|
| **Прикидка** | Вилка «от–до» для разговора с клиентом | ±40%, устно/в чате |
| **Смета** | Постатейный расчёт по этапам | Финальная, идёт в КП |
| **Обоснование НМЦ** | Документ по методике заказчика | Формальная, идёт в заявку |

Прежде чем считать — определи, какая из трёх. Прикидку не оформляют как смету,
смету не выдают за обоснование НМЦ.

---

## Железное правило: цифры не выдумываются

Это главное в скилле. Смета — документ с финансовыми последствиями; выдуманная цифра
стоит дороже любой сэкономленной минуты.

**Перед любым расчётом прочитай `memory/pricing.md`.**

Если нужные поля там помечены `[ЗАПОЛНИТЬ]` — **остановись и запроси цифры у человека**.
Не бери «рыночные» значения, не оценивай «по аналогии с индустрией», не ставь
правдоподобную заглушку. Правильная реакция:

> Для расчёта нужны ставки: backend, frontend, дизайн. В `memory/pricing.md` они не заполнены.
> Назови их или скажи, откуда взять.

**Различай инициативу и указание.** Если человек сам назвал цифру («ставка 3500»,
«поставь за этап 400 тысяч») — это указание, применяй сразу. Границы касаются только того,
что агент собирается придумать сам.

Отдельно: **итоговую цену для клиента утверждает руководитель.** Агент считает и предлагает
расчёт, но не объявляет финальную цену как решённую.

## Что клиент видит, а что нет

Жёсткое правило из `memory/rules.md`, нарушать нельзя:

| Внутренний расчёт | В клиентском документе |
|---|---|
| Часы по задачам | ❌ никогда |
| Ставка ₽/час | ❌ никогда |
| Суммарные часы | ❌ никогда |
| Разбивка по ролям | ❌ никогда |
| Маржа, резерв на риски | ❌ никогда |
| | ✅ стоимость по этапам / блокам |
| | ✅ состав работ внутри этапа словами |
| | ✅ итог, НДС, срок |

Почему: раскрытая ставка и объём дают основание торговаться по каждой строке и обнажают
структуру маржи.

Практически это значит: **два файла, не один.** Внутренний расчёт с часами остаётся
в папке проекта и не уходит клиенту. Клиентская смета собирается из него агрегацией.
Если заказчик своей формой требует указать часы — это исключение, эскалируй человеку,
не решай сам.

## Порядок работы

### 1. Собрать исходные данные

Перед декомпозицией должно быть на руках:

- ТЗ или описание скоупа
- форма, в которой заказчик ждёт цену (часто своя таблица — `Форма ТКП`, `Форма №3`,
  `Приложение — форма ответа КП`)
- срок и этапность, если заданы
- под каким юрлицом подаём (влияет на НДС) — спросить, если не сказано

Чего не хватает — спроси до расчёта, а не после.

### 2. Декомпозировать скоуп

Разбей работу на блоки, по которым потом собирается смета. Типовая структура для
веб-проекта:

1. Аналитика и требования
2. Проектирование (вайрфреймы — **только десктоп**, см. `memory/rules.md`)
3. Дизайн
4. Вёрстка
5. Разработка (frontend / backend / интеграции)
6. Наполнение контентом
7. Тестирование
8. Запуск и передача
9. Техподдержка (отдельным блоком, часто отдельным договором)

Для ИИ-решений добавляются: подготовка данных, интеграция с источниками знаний,
настройка и оценка качества модели, дообучение/промпт-инжиниринг.

Блок, которого в ТЗ нет, но который очевидно нужен для работоспособности — **назови
человеку отдельно**, не добавляй в смету молча. Это расширение скоупа.

### 3. Оценить трудоёмкость

Источник ориентиров — `memory/pricing.md`, раздел «Ориентиры по трудоёмкости»,
откалиброванный по прошлым сметам. Файлы-образцы перечислены там же.

Если для блока ориентира нет — оценивай по ближайшему аналогу из портфолио и **пометь
оценку как требующую проверки**. Не выдавай её за откалиброванную.

### 4. Посчитать

Трудоёмкость × ставка → себестоимость блока. Сверху — параметры из `memory/pricing.md`:
управленческая надбавка, резерв, НДС, округление.

### 5. Собрать два документа

- **Внутренний**: часы, роли, ставки, маржа. В папку проекта.
- **Клиентский**: по этапам, без часов и ставок. В форме заказчика, если она задана.

### 6. Проверить перед отдачей

- сумма клиентской сметы = сумме внутреннего расчёта (после округлений)
- ни одной ячейки с часами или ставкой в клиентском файле
- форма заказчика заполнена целиком, включая поля, которые кажутся необязательными
- НДС указан в соответствии с юрлицом
- если есть лимит НМЦ — итог его не превышает

## НМЦ / НМЦД

Начальная (максимальная) цена договора. Считается **не нами** в свою пользу, а по методике,
заданной заказчиком.

Основной метод — **сопоставимых рыночных цен**: собираются коммерческие предложения
(обычно не менее 3), считается среднее, проверяется коэффициент вариации.

**Методику, формулы и состав приложений бери из документации конкретного тендера,
не из общего знания.** Они различаются между площадками и заказчиками. Файл с методикой
обычно называется «Определение НМЦД», «Обоснование НМЦ» или лежит приложением к извещению.

Образец из прошлого тендера: `projects/Воксис/4.1  Определение НМЦД 17055043 (1) (1).xlsx`.

Если наша цена должна укладываться в объявленную НМЦ — это ограничение сверху,
проверяй его до того, как собирать документ.

## Технические заметки

**Excel.** `openpyxl`. Объединённые ячейки после записи разъезжаются — пересобирать merge
после изменения. Формулы `openpyxl` не пересчитывает: либо писать значения, либо гнать файл
через пересчёт.

**Формы заказчика не переверстывать.** Заполняются существующие ячейки. Изменённая
структура формы — основание отклонить заявку. Не добавляй строки и столбцы в чужой шаблон,
даже если так логичнее; если строк не хватает — спроси человека.

**Кириллица в именах файлов** ломает часть библиотек — копировать в рабочую папку
с ASCII-именем перед обработкой.

**Проверяй тип файла, а не расширение.** Часть присланных «.xlsx»/«.docx» на деле —
другие форматы или ZIP-архивы.

## Формат ответа

- посчитал → вот внутренний расчёт → вот клиентская смета → что осталось открытым
- допущения, на которых стоит расчёт, — **явным списком**, а не растворённые в тексте
- цифры, требующие подтверждения руководителя, — отдельно и заметно
