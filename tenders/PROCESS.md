# Тендерный пайплайн

Процесс подготовки тендера от «прислали документацию» до «заявка собрана».
Структура папок повторяет процесс: одна стадия — одна папка.

---

## Структура тендера

```
tenders/<Тендер>/
├── STATUS.md          ← состояние, паспорт, решения, лог. Читается первым
├── 00-source/         ← документация как пришла, не редактируется
├── 01-analysis/       ← разбор тендера, вывод об участии
├── 02-estimate/       ← расчёты: внутренний + клиентский
├── 03-proposal/       ← КП, презентация
└── 04-application/    ← формы, документы заявки, чек-лист
```

`00-source/` — **неприкосновенный и вне git** (в `.gitignore`). Исходники не правятся
никогда: если понадобилась правка, файл копируется в рабочую стадию. Восстановимы из
письма/площадки заказчика — версионировать незачем. Их состав фиксируется не файловой
системой, а таблицей «Опись» в `STATUS.md` — это единственный след в репозитории.

Имя папки тендера — по заказчику: `ГРК`, `Воксис`, `Движение Первых`.
Если у заказчика два тендера — добавляется предмет: `ГРК — карьерный сайт`.

## Стадии

| № | Стадия | Агент | Обязательна | Выход |
|---|---|---|---|---|
| 0 | Приёмка документации | `tender-intake` | да | `00-source/` + опись в `STATUS.md` |
| 1 | Анализ участия | `tender-analyst` | по необходимости | `01-analysis/ЗАКЛЮЧЕНИЕ.md` |
| 2 | Деньги | `tender-estimate` | по необходимости | `02-estimate/` — 2 файла |
| 3 | КП и презентация | `tender-deck` | обычно да | `03-proposal/` — PDF/PPTX |
| 4 | Документы заявки | `tender-docs` | по необходимости | `04-application/` — чек-лист + формы |
| R | Проверка перед отправкой | `tender-reviewer` | рекомендуется | `ЗАМЕЧАНИЯ.md` рядом с проверенным артефактом |

Стадия R — не по порядку с остальными: вызывается после 2/3/4, когда результат готов
к показу заказчику или человеку. Только читает и находит нарушения накопленных
в `memory/rules.md` правил и типовых ошибок (дубли картинок, нерелевантные скриншоты
в портфолио, утечка часов/ставки в клиентскую смету и т.п.) — ничего не правит сама.

Стадии 1, 2, 4 — **по необходимости**. Пропуск стадии фиксируется в `STATUS.md` строкой
«пропущено, причина». Молча пропускать нельзя — через месяц не вспомнить, забыли или решили.

Стадии не обязаны идти по порядку. Смета часто нужна до анализа (чтобы понять, проходим
ли по НМЦ), КП правится после сборки заявки. Порядок в таблице — типовой, не жёсткий.

## Как идёт работа

Человек разговаривает **только с оркестратором**. Оркестратор:

1. Читает `STATUS.md` тендера — понимает, где мы
2. Определяет стадию и вызывает нужного агента
3. Передаёт агенту **явно**: путь к папке тендера, задачу, что уже сделано
4. Получает результат, показывает человеку
5. Обновляет `STATUS.md`

Агент стартует без контекста разговора. Всё, что ему нужно, — в задании и в `STATUS.md`.

`STATUS.md` пишет **только оркестратор**. Агент возвращает результат текстом в ответе —
оркестратор переносит нужное в файл. Один писатель — нет гонки при параллельном запуске
и гарантия, что оркестратор видел всё, что попало в состояние.

### Параллельный запуск

Разрешён только для пар из таблицы ниже. Список — рабочий и правится вручную, когда
понимание зависимостей меняется; не жёсткая техническая привязка.

| Пара | Параллельно? | Почему |
|---|---|---|
| `tender-analyst` + `tender-estimate` | ✅ | независимы |
| `tender-analyst` + `tender-deck` | ✅ | deck зависит от estimate, не от analyst |
| `tender-deck` + `tender-docs` | ✅ | разные выходы, не пересекаются |
| `tender-estimate` + `tender-deck` | ❌ | deck читает цифры из `02-estimate/` |
| `tender-estimate` + `tender-docs` | ❌ | docs может требовать смету в форме заказчика |

Вне списка — по умолчанию последовательно.

### Кто решает, что нужна стадия

После стадии 0 у оркестратора на руках вся документация. Он читает её и **предлагает**
маршрут: какие стадии 1/2/4 нужны и почему («анализ нужен — требования нетиповые»,
«смета не нужна — цена фиксирована заказчиком»). Финальное решение — за человеком.

### Возврат и правки

К любой стадии можно вернуться в любой момент. Правка — это не новый проход стадии,
а точечное изменение:

- «поправь слайд 7» → `tender-deck`, меняется только слайд 7
- «пересчитай с учётом скидки 10%» → `tender-estimate`, пересобираются оба файла
- «добавь требование, которое пропустили» → `tender-docs`

После правки, затрагивающей другие стадии, — **проверь связанное**. Изменилась смета →
цифры в КП устарели. Оркестратор обязан это заметить и сказать, а не молча оставить
рассинхрон. В `STATUS.md` есть раздел «Зависимости» именно для этого.

Механика проверки — по датам. Каждая отметка стадии в `STATUS.md` несёт дату. Если дата
стадии-источника (например, `02-estimate`) новее даты стадии-потребителя (`03-proposal`) —
потребитель устарел, оркестратор сообщает об этом перед тем, как отдавать файл дальше.

### Версии внутри стадии

Один файл на стадию, правки — перезапись. Версия в имени файла (`_v1`, `_v2`) растёт
только на существенном пересмотре — новая цена, новый скоуп, — не на точечной правке
(«поправь слайд 7» не создаёт `_v2`). Иначе за месяц работы над тендером накапливается
десяток файлов, из которых непонятно, какой актуален.

### Когда уместен loop

`/loop` — для повторяющейся проверки, не для творческой работы:

- отслеживание дедлайна подачи, когда до него больше суток
- мониторинг площадки на ответы заказчика по разъяснениям
- итеративная доводка вёрстки: проверка переполнения → правка → проверка

Не использовать loop для генерации содержания: КП не улучшается от того, что его
переписали пять раз без обратной связи от человека.

## Правила, общие для всех стадий

1. **Цифры не выдумываются.** Ни цена, ни срок, ни объём. Нет данных — спросить.
   Подробности — `memory/pricing.md` и `AGENTS.md` §6.
2. **Требования цитируются, не пересказываются.** «Опыт от 3 лет» и «опыт не менее 3 лет
   по аналогичным договорам» — разные требования.
3. **Разрывы называются прямо.** Если чему-то не соответствуем — это должно быть видно
   до подачи, а не после.
4. **Формы заказчика не переверстываются.** Заполняются существующие ячейки; изменённая
   структура формы — основание отклонить заявку.
5. **Минимальное касание.** Просят поправить одно — меняется одно.

## Архив

Завершённый тендер (выиграли, проиграли, не подавались) остаётся на месте.
В `STATUS.md` проставляется финальный статус и дата в разделе «Решение об участии».
Не переносить в отдельный архив — прошлые тендеры это калибровочная база для смет
и источник формулировок.

Тендеры, начатые до введения этого пайплайна и оставшиеся в `projects/` (не мигрированы),
получают лёгкий `STATUS.md` по шаблону `_templates/STATUS-архив.md` — без стадий, только
статус и дата закрытия. Это сигнал агенту не продолжать работу без нового явного указания.
