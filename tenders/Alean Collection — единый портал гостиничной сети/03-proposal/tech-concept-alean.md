# Техническая концепция единого портала Alean Collection

Верхнеуровневое предложение на этапе выбора подрядчика

---

## 0. Резюме в одном абзаце

Мы предлагаем headless-архитектуру: **1С-Битрикс остаётся системой хранения контента и админкой, витрина строится на Next.js**. Между ними — собственный контентный API с фиксированным контрактом, благодаря которому CMS перестаёт быть частью фронтенда и в будущем может быть заменена без переписывания портала. Портал проектируется не как «10 подсайтов», а как **каталог отелей + библиотека универсальных блоков + система брендовых тем**, поэтому добавление 11-го или 21-го отеля — работа контент-менеджера, а не разработчика. Практически весь пользовательский трафик обслуживается предсобранной статикой через CDN, что закрывает требования по нагрузке и Core Web Vitals архитектурой, а не стоимостью инфраструктуры.

## 1. Что мы увидели в текущих сайтах

Анализ выполнен по открытым данным 10 сайтов до начала работ.

**Все 10 сайтов работают на одном шаблоне 1С-Битрикс** (`/local/templates/alean/`): совпадают шапка, футер, набор попапов, формы и — что важнее всего — структура URL:

```
/promotions/   /nomera-price/   /restaurant/   /kids/
/beauty-health/   /entertainment/   /news/   /poster/
/contacts/   /transfer/   /tour/   /reviews/   /documents/
```

Это принципиально влияет на оценку проекта. Миграция — не десять разных задач, а одна повторяющаяся: **правило `hotel.ru/{path}` → `portal.ru/hotels/{slug}/{path}` покрывает основную массу URL автоматически**, вручную разбираются только кастомные лендинги (`/rannee-bronirovanie/` у Doville, `/leto-v-gorakh/` и `/aktivnyy-otdykh-v-gorakh/` у Pino). Контент-модель уже унифицирована на уровне инфоблоков, поэтому выгрузка предсказуема и скриптуема.

**Текущий контур интеграций:**

| Компонент | Решение | Роль в новом портале |
|---|---|---|
| CMS | 1С-Битрикс: Управление сайтом | Сохраняется как backend и админка |
| Бронирование | TravelLine (`booking.aleancollection.ru?hotel={UUID}`) | Сохраняется, интеграция через виджет и deeplink |
| CRM | Битрикс24 | Приёмник лидов со всех форм |
| Email-маркетинг | Mindbox | Сохраняется, подписки через API |
| Аналитика | Яндекс.Метрика (счётчик отеля + сводный) | Схема сохраняется и достраивается |

**Дефекты, которые портал закрывает по ходу:**

- **Рассинхрон возраста детей.** В форме подбора номера — «дети до 12 лет», в действующей акции и в ТЗ — «дети до 15 лет бесплатно». Расхождение находится ровно на главном УТП сети и работает против конверсии.
- **У новостей нет собственных URL.** Материалы раскрываются в попапе (`#news-detail-popup-inner`), то есть не индексируются. На 10 сайтах это накопленный объём контента, не приносящий органического трафика.
- **Изображения отдаются в JPEG** через `resize_cache`, без WebP/AVIF и без полноценного `srcset`. При требовании LCP < 2,5 с это первое узкое место.
- **Единого личного кабинета нет.** Программа лояльности описана, но регистрации на сайте не существует; «Управление бронированием» уводит в TravelLine.
- **Фактический масштаб превышает описанный в ТЗ.** На сайте представлены 21 отель и 7 брендов, из них 11 отелей уже живут страницами внутри `/hotels/{slug}/`. Архитектуру имеет смысл проектировать под фактический масштаб, а не под 10 доменов.

## 2. Выбор платформы

### 2.1. Рассмотренные варианты

| Вариант | Плюсы | Ограничения |
|---|---|---|
| **А. Эволюция на Битриксе** (многосайтовость БУС) | Минимальная миграция, персонал не переучивается, самая низкая стоимость | Тяжело выйти на целевые Core Web Vitals, ограниченная свобода фронтенда, слабо отвечает требованию «актуально длительное время» |
| **Б. Битрикс (backend) + Next.js (витрина)** | Соответствует опции, названной в ТЗ; контент остаётся в знакомой системе; современный фронт и CWV; миграция внутри Битрикса | Требуется компетенция в двух стеках; чуть выше стоимость запуска |
| **В. Greenfield: Strapi/Directus + Next.js** | Самая чистая контент-модель, лучшая админка под конструктор блоков | Дорогая миграция, полное переобучение редакции, Битрикс всё равно остаётся в контуре как CRM |

### 2.2. Рекомендация

**Вариант Б как основа, с заложенным путём к В.**

Битрикс остаётся системой записи на момент запуска — это снимает риски миграции и переобучения. Но фронтенд с первого дня работает через собственный контентный API, а не через внутренние структуры CMS. Следствие: замена CMS в будущем — это проект на недели (переписать адаптер под тот же контракт), а не пересборка портала.

> **Терминологическое уточнение к ТЗ.** В разделах 1 и 6 платформой назван «Битрикс24» — это CRM и корпоративный портал. Сайты сети работают на «1С-Битрикс: Управление сайтом» (БУС). В ФТ-5 при этом верно указано, что формы интегрируются с Битрикс CRM. В концепции мы исходим из прочтения: **БУС — сайт, Битрикс24 — CRM**. Просим подтвердить.

│  Next.js                │   │  TravelLine             │
│  SSG + ISR + API routes │   │  (виджет / deeplink)    │
└──────────┬──────────────┘   └─────────────────────────┘

┌──────────┴──────────────────────────────────────────────┐
│  1С-Битрикс: Управление сайтом                          │

└──────────┬───────────────────────┬──────────────────────┘
           │                       │
┌──────────┴────────┐   ┌──────────┴──────────┐

Внешние: Битрикс24 (CRM) · Mindbox · Яндекс.Метрика

### 3.2. Контентный API

Ключевое решение — **не отдавать наружу внутренние структуры Битрикса**. Реализуется модуль БУС, публикующий нормализованные DTO по собственному контракту:

- REST + JSON, версионирование через путь (`/api/v1/...`)
- Спецификация OpenAPI 3.0 с Swagger UI
- Курсорная пагинация для списков
- Ошибки в формате RFC 7807
- Webhook-события при публикации контента (триггер ISR-ревалидации)

Контракт принадлежит проекту, а не CMS. Именно это делает платформу заменяемой и является основным ответом на требование «подход к развитию портала в будущем».

### 3.3. Стратегия рендеринга

Это центральное решение, от которого зависят и производительность, и стоимость инфраструктуры.

| Тип страницы | Режим | Обоснование |
|---|---|---|
| Главная, страницы отелей, услуги, акции, новости, гайды | **SSG + ISR** с ревалидацией по webhook из админки | Контент меняется редко и предсказуемо; пользователь всегда получает статику из кеша |
| Каталог отелей с фильтрами | Статическая оболочка + **клиентская фильтрация** по предзагруженному JSON | 21 отель — это единицы килобайт. Серверный поиск не нужен: фильтры срабатывают мгновенно и не создают нагрузки на бэкенд вообще |
| Цены «от» | Отдельный edge-эндпоинт с коротким TTL, источник — TravelLine | Изолирует волатильные данные от статики |
| Формы, поиск номера | API routes → очередь → Битрикс24 | Единственный по-настоящему динамический контур |

**Следствие для нагрузочных требований.** Основной трафик — статика на CDN, а он масштабируется практически бесплатно. Реально динамических запросов остаётся малая доля. Мы отвечаем на требование 2 000 RPS **дизайном системы, а не размером кластера** — и подтверждаем это нагрузочным тестированием на этапе 3.

## 4. Контент-модель

Принцип: **не плодить типы сущностей, плодить блоки**. Страница — это упорядоченный массив блоков; каждый блок — тип, данные и настройки отображения.

**Справочники (задаются один раз, переиспользуются везде):**

| Сущность | Содержание |
|---|---|
| `Brand` | 7 брендов: токены темы, логотип, слоган, тональность, описание |
| `Destination` | 8 городов: гайды, достопримечательности, как добраться, схемы проезда |
| `Facility` | Единый справочник услуг и удобств — источник фасетов каталога |
| `MealPlan` | Ультра всё включено / Всё включено / Завтраки / Полный пансион |

**Основные сущности:**

| Сущность | Ключевые поля |
|---|---|
| `Hotel` | бренд, локация, звёздность, концепция питания, набор `Facility`, UUID TravelLine, «фишка», галерея, SEO-блок |
| `RoomCategory` | отель, площадь, число комнат, вместимость, оснащение, фото |
| `Promotion` | **scope**: вся сеть / бренд / список отелей; срок акции и период проживания раздельно; условия |
| `InfraObject` | ресторан, бар, СПА-программа, детский клуб, академия, площадка — один тип с категорией вместо десяти инфоблоков |
| `Page` | массив блоков, тема, SEO |
| `Event` / `NewsItem` / `Review` / `Vacancy` / `Tender` / `Document` | контентные типы с собственными URL |

Отдельно отмечаем: **новости и события получают полноценные индексируемые URL** — это исправление текущей ситуации с попапами и возврат уже накопленного контента в органический поиск.

## 5. Библиотека блоков — ответ на ключевое требование ТЗ

> «Все блоки конструктора должны быть универсальны и без дополнительных доработок иметь возможность встраиваться на любую страницу сайта и иметь опцию адаптивного дизайна под тот или иной бренд.»

Это требование мы считаем центральным: на нём одновременно закрываются масштабируемость, удобство редактирования, брендирование и развитие. Базовая библиотека — порядка 25–30 блоков:

**Навигация и точки входа:** Hero (полноэкранное медиа / слайдер / видео), форма подбора номера, закреплённый мобильный виджет бронирования, CTA-баннер, счётчик обратного отсчёта (ФТ-8), хлебные крошки.

**Каталог и продукт:** сетка отелей с фильтром по бренду и локации, карточки номеров, таблица категорий, блок концепции питания, карта объектов.

**Контент:** текст + медиа (лево/право), аккордеон и FAQ, таймлайн, цифры и статистика, галерея с категориями, сетка услуг инфраструктуры, афиша-календарь, лента новостей, отзывы, награды, логотипы партнёров.

**Конверсия:** четыре типа форм из ФТ-5 (обратный звонок, заявка на бронирование, поп-ап, универсальная). **Каждая форма на каждой странице — независимый экземпляр** с собственными настройками, получателями и целями аналитики, как и требует ТЗ.

Каждый блок поставляется с описанным контрактом свойств, набором вариаций и поддержкой брендовых токенов. Артефактом приёмки выступает **Storybook** — живая витрина блоков, по которой заказчик проверяет полноту библиотеки до сборки страниц.

## 6. Система тем: как один портал носит семь брендов

Трёхуровневая система токенов на CSS custom properties:

1. **Ядро** — сетка, шкала отступов, брейкпоинты (от 360 px), скорости анимаций. Общее для всего портала, обеспечивает единство.
2. **Бренд** — палитра, типографика, радиусы, стиль кнопок и карточек. Семь наборов: Family, Club, Select, Extency, Health, Emerald, Residence.
3. **Контекст** — «Море» / «Горы». Фоновая фактура, акцентный слой, иллюстративные элементы.

Тема применяется на уровне layout подсайта через атрибуты `data-brand` и `data-context` — **без пересборки и без участия разработчика**.

> Мы обратили внимание, что прототипы в ТЗ названы «Море» и «Горы», а не по брендам. Это подтверждает, что тематизация у сети фактически двухмерная: бренд × локация. Токен-система описывает обе оси, а не одну.

**Практический смысл:** новый бренд — это заполненный набор токенов в админке. Новый отель — запись в каталоге. Ни то, ни другое не требует релиза.

## 7. Маршрутизация и URL

### 7.1. Расхождение внутри ТЗ

Таблица в п. 1.1 задаёт подсайты как `/dovilleresort`, а ФТ-2.4 требует схему `/hotels/{slug}/`. Варианты взаимоисключающие.

**Рекомендуем `/hotels/{slug}/`.** Обоснование:

- корневые сегменты вида `/dovilleresort` при росте до 21 отеля конкурируют за пространство имён с системными разделами (`/about`, `/news`, `/mice`, `/career`, `/partners`, `/development`);
- иерархия «портал → каталог → отель» яснее читается поисковыми системами и естественно ложится в хлебные крошки и микроразметку;
- совпадает со схемой, по которой **уже живут 11 отелей** на текущем головном сайте — то есть часть URL не придётся менять вовсе.

При этом закладываем поддержку коротких vanity-путей `/{slug}` с 301 на канонический адрес — если заказчик предпочтёт их для оффлайн-рекламы.

### 7.2. Структура

```
/                                   главная
/hotels/                            каталог с фасетами
/hotels/{slug}/                     подсайт отеля
/hotels/{slug}/{section}/           раздел отеля
/hotels/{slug}/nomera-price/{room}/ категория номера
/promotions/  /loyalty/  /news/  /events/  /guides/
/about/  /contacts/  /development/  /career/  /mice/  /partners/
```

Каждый подсайт отеля и каждая страница поддерживают индивидуальные Title, Description, H1 и микроразметку (ФТ-2.5).

## 8. Миграция и сохранение поисковых позиций

Самый рискованный участок проекта — и одновременно тот, где однотипность текущих сайтов работает нам на руку.

### 8.1. Процесс

1. **Инвентаризация.** Сбор `sitemap.xml` со всех 10 доменов, полный краулинг, выгрузка топа страниц по трафику из Яндекс.Метрики и списка страниц с внешними ссылками из Вебмастера. Результат — единый реестр URL с приоритетами.
2. **Автоматический мэппинг** по правилу сохранения пути. Ожидаемое покрытие — основная масса адресов.
3. **Ручной разбор остатка:** кастомные лендинги, страницы с изменившейся структурой, новости, впервые получающие собственные URL.
4. **Валидация до релиза:** ноль цепочек редиректов, ноль циклов, каждый целевой адрес отдаёт 200.
5. **Реализация карты на уровне reverse proxy** (nginx `map` / Redis), а не в коде приложения — правки без релиза.
6. **Постмиграционный контроль:** мониторинг 404, переиндексация в Вебмастере, еженедельный отчёт по позициям и трафику в течение 8 недель.

**Обратимость (ФТ-7.3):** миграция идемпотентна. Источник истины — старая база, целевая структура пересобирается с нуля любое число раз без потери данных.

### 8.2. Волновое переключение вместо одномоментного

Склейка десяти доменов с накопленной историей в один даёт закономерную просадку органики на первые недели. Величина зависит от качества карты редиректов, но нулевой она не бывает никогда.

При цикле 6–7 месяцев и старте договора осенью момент переключения приходится на **весну — то есть на пик раннего бронирования**. Проседание органики в этом окне конвертируется напрямую в недополученную выручку.

**Предлагаем:**

- **Волна 1** — один-два отеля с наименьшим органическим трафиком, в низкий сезон. Замер 3–4 недели.
- **Волны 2–3** — остальные отели, с уже проверенной на практике картой редиректов.
- **Домены не высвобождаются.** Продлеваются и остаются редирект-хостами: они присутствуют в закладках, в печатных материалах и в оффлайн-рекламе.
- **Целевые окна переключения:** сентябрь–ноябрь либо период после майских праздников.

Это отличается от формулировки этапа 4 в ТЗ («переключение трафика с 10 сайтов»). Мы считаем важным проговорить это до подписания, а не после.

## 9. Нефункциональные требования: подход разумной достаточности

Часть требований раздела 6 ТЗ, на наш взгляд, задана с запасом, характерным для высоконагруженных транзакционных систем. Ниже — что мы предлагаем и почему. Мы готовы реализовать требования и в исходной формулировке, но считаем правильным показать разницу в стоимости владения.

| Требование ТЗ | Наше предложение | Обоснование |
|---|---|---|
| Пик 2 000 RPS | Принимаем как приёмочный критерий нагрузочного теста, но обслуживаем статикой на CDN | 2 000 RPS — порядка 170 млн запросов в сутки, что на порядок с лишним превышает реальный профиль сети из 21 отеля. Статика такую нагрузку держит; строить под неё кластер приложений не требуется |
| 500 одновременных оформлений броней | Бронирование выполняется в TravelLine — это их контур и их SLA. Наша задача: виджет не влияет на устойчивость портала | Соответствует прямому замечанию ТЗ: «нагрузка на модуль может перегружать сайт, необходимо этого избежать». Решается изоляцией, отложенной загрузкой и circuit breaker |
| Rate limit ≥ 10 000 запросов/мин на IP | Дифференцированные лимиты: публичные эндпоинты ~600/мин на IP, формы ~60/мин на IP, глобальный потолок на эндпоинт | 10 000 в минуту с одного адреса — это 166 запросов в секунду с одного источника. Такой лимит не выполняет защитной функции; вероятно, в ТЗ он перепутан с общим лимитом на эндпоинт |
| HashiCorp Vault | Секреты в managed-хранилище облака (Yandex Lockbox или аналог) + защищённые переменные CI | Требование «не хранить секреты в коде» выполняется полностью; отдельный кластер Vault для контура такого размера — избыточная стоимость эксплуатации |
| Jaeger / Zipkin | OpenTelemetry с экспортом в Grafana Tempo | Распределённая трассировка проектируется под микросервисы. У нас витрина и один API; OTel даёт наблюдаемость сейчас и путь к полноценному трейсингу при росте |
| ELK-стек | Loki + Grafana (вариант, прямо допущенный ТЗ) | Существенно ниже требования к ресурсам при сопоставимой функциональности для этого объёма логов |
| Микросервисная архитектура | Не предлагается | Портал не декомпозируется по бизнес-доменам, требующим независимого масштабирования. Микросервисы здесь добавляют стоимость эксплуатации, не добавляя устойчивости |

**Что берём без изменений:** SLA 99,9%, отсутствие единых точек отказа, репликация БД с автоматическим failover, ежедневные полные бэкапы с непрерывным архивированием журналов и хранением 30 дней, откат за 5 минут, graceful degradation при недоступности внешних сервисов, соответствие 152-ФЗ, OWASP Top-10, HSTS и TLS 1.2+, RBAC, audit log 12 месяцев, WAF, целевые Core Web Vitals.

## 10. Инфраструктура и эксплуатация

**Размещение:** облачная инфраструктура на территории РФ (Yandex Cloud / VK Cloud / Selectel — финальный выбор по согласованию с учётом действующих договоров заказчика).

- **Вычисления:** приложение за балансировщиком с автомасштабированием; управляемая MySQL с репликой primary–replica и автоматическим failover
- **Хранилище:** S3-совместимое объектное хранилище для медиа, бэкапов и логов
- **CDN:** российский CDN перед статикой и медиа
- **Изображения:** автоматическая конвертация в WebP/AVIF, генерация `srcset`, ленивая загрузка — прямое устранение текущего узкого места по LCP
- **CI/CD:** GitLab CI — сборка, линтеры, тесты, деплой
- **IaC:** Terraform для инфраструктуры, Ansible для конфигураций
- **Контуры:** dev / staging / production в изоляции; staging закрыт авторизацией и `noindex`; административный доступ через VPN
- **Релизы:** blue-green с переключением upstream, откат менее чем за 5 минут
- **Мониторинг:** Prometheus + Grafana, алертинг P1 в пределах минуты, P2 — пяти; health-эндпоинты `/health`, `/ready`, `/live`
- **Логи:** Loki, 90 дней в горячем хранении, архив — год

## 11. Управление контентом

**Роли (ФТ-4)** реализуются группами пользователей Битрикса с правами на уровне инфоблоков и разделов:

| Роль | Права |
|---|---|
| Администратор | Полный доступ, управление пользователями |
| Контент-менеджер сети | Все отели и разделы, создание подсайтов и страниц, редиректы, SEO |
| Контент-менеджер отеля | Только свой отель |
| Департамент качества | **Только** инфоблок отзывов — модерация и публикация, без доступа к остальным разделам |
| SEO-специалист | Метатеги, ЧПУ, редиректы, sitemap — без прав на контент |

Все действия в админке пишутся в audit log с хранением 12 месяцев.

**Рабочий процесс редактора:** страница собирается из блоков, доступных в общей библиотеке; предпросмотр в брендовой теме доступен до публикации; после публикации webhook запускает точечную ревалидацию затронутых страниц — обновление появляется на сайте за секунды, без пересборки портала.

**Обучение и передача:** два вебинара для сотрудников заказчика, инструкция администратора CMS, Storybook как справочник по блокам, две недели горячей линии после запуска, гарантия на исправление ошибок 6 месяцев.

## 12. Масштабирование и развитие

Три горизонта, отвечающих на требования ТЗ к участнику.

**Контентное масштабирование.** Новый отель — запись в каталоге, наследующая тему бренда и шаблоны разделов. Новый бренд — набор токенов. Новый тип страницы — комбинация существующих блоков. Ни один из сценариев не требует релиза. Это ключевая причина, по которой мы проектируем под фактические 21 отель и 7 брендов, а не под 10 доменов из ТЗ.

**Техническое масштабирование.** Статика горизонтально масштабируется через CDN; динамический контур — автоматическим масштабированием реплик приложения; база — чтением с реплик. Узкие места выявляются нагрузочным тестированием на этапе 3 по сценариям пиковых сезонов.

**Продуктовое развитие.** Заложены точки роста, не входящие в блок «Запуск», но не требующие переделки архитектуры:

- личный кабинет гостя и программа лояльности с историей бронирований;
- вторая языковая версия — архитектура мультиязычна изначально, требуется только перевод контента;
- персонализация выдачи каталога и подборок;
- расширение API для партнёров через webhook-подписки;
- вынос контента в отдельную headless CMS при необходимости — благодаря фиксированному контракту API это замена адаптера, а не переписывание портала.
